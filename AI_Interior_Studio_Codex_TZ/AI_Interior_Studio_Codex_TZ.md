# AI Interior Studio — полное техническое задание для Codex

**Версия:** 1.0  
**Формат:** самостоятельное техническое задание для создания веб-приложения  
**Цель:** разработать коммерчески расширяемый ИИ-визуализатор интерьера, который преобразует загруженную фотографию помещения в фотореалистичный вариант нового дизайна.

> **Инструкция Codex:** используй этот файл как главный документ проекта. Выполняй работы поэтапно, не выдавай демонстрационные функции за настоящие и после каждого этапа проверяй результат. Если здесь не указан конкретный параметр внешнего API, изучи актуальную официальную документацию и используй поддерживаемое поведение; не выдумывай интерфейсы API.

---

## 1. Концепция и границы

Пользователь загружает фотографию существующего помещения, выбирает тип комнаты, интерьерный стиль, палитру и перечень изменений, при необходимости пишет пожелания, затем запускает генерацию. Система использует **саму фотографию как вход для редактирования**, а не генерирует случайную комнату только по тексту. Результат можно сравнить с исходником, скачать и сохранить в личном кабинете.

**Аудитория:** частные владельцы квартир и домов, дизайнеры интерьера, риелторы, ремонтные компании.  
**Платформы:** адаптивное веб-приложение для компьютеров, планшетов и смартфонов.  
**Языки:** английский (по умолчанию) и русский; архитектура локализации должна допускать добавление языков.

**Входит в MVP:** главная страница, визуализатор, загрузка фото, шесть основных стилей, параметры преобразования, демонстрационный режим, реальное редактирование изображений через ИИ, сравнение до/после, скачивание, регистрация, приватные проекты и история результатов, основные страницы настроек и документация.

**Не входит в MVP:** точный 3D-конструктор, обмер помещения по фотографии, чертежи, строительные расчёты, полноценный каталог товаров, гарантированная геометрическая точность, работающая подписка или приём платежей. Подготовить возможность добавить эти функции в будущем.

## 2. Технологический стек

- **Клиент:** Next.js с App Router, React, TypeScript в строгом режиме, Tailwind CSS, shadcn/ui, Lucide.
- **Сервер:** Next.js Route Handlers; отдельные сервисы для генерации, файлов, проектов и лимитов.
- **ИИ:** OpenAI Images API с редактированием входной фотографии. Модель, качество, формат и размеры задаются через конфигурацию и должны соответствовать актуальной документации.
- **База данных:** PostgreSQL через Supabase.
- **Авторизация:** Supabase Auth, подтверждение электронной почты, восстановление пароля.
- **Файлы:** приватные бакеты Supabase Storage; краткоживущие подписанные ссылки или авторизованные маршруты для доступа.
- **Валидация:** Zod на сервере; клиентская валидация только как дополнение.
- **Тесты:** Vitest для модульных/интеграционных тестов и Playwright для E2E.
- **Размещение:** Vercel или эквивалент для веб-приложения; отдельный надёжный механизм фонового выполнения для долгих генераций.
- **Версионирование:** Git и GitHub.

Перед установкой сверить актуальные совместимые версии библиотек и требования официальных документаций. Не полагаться на устаревшие сигнатуры методов.

## 3. Дизайн-система

Стиль интерфейса: минималистичный премиальный продукт с крупными интерьерными изображениями, спокойными цветами, ясной типографикой и максимально простой формой генерации.

**Палитра:** фон `#FAF9F6`, текст `#202020`, дополнительный текст `#717171`, акцент `#B28C64`, карточки `#FFFFFF`, границы `#E8E5DF`, тёмные кнопки `#252525`.

Использовать переиспользуемые компоненты, единые отступы и радиусы. Предусмотреть архитектуру для тёмной темы. Управление должно работать с клавиатуры, поля должны иметь подписи, текст и элементы интерфейса — достаточную контрастность.

**Адаптивность:** на десктопе визуализатор имеет панель настроек рядом с крупной областью просмотра; на телефоне — вертикальное расположение либо выдвижную панель. Состояние заполненной формы должно сохраняться при переключении между вкладками интерфейса.

## 4. Страницы

### 4.1. Главная `/`
Шапка: логотип, навигация, выбор языка, вход и основная кнопка «Create design». Первый экран: крупная интерьерная фотография, понятный заголовок, описание и CTA. Далее — «Как это работает», доступные стили, примеры, преимущества, FAQ, подвал. Изображения использовать только с подходящими правами.

### 4.2. Студия `/studio`
Загрузка фотографии, выбор помещения, стиля и палитры, список изменяемых элементов, дополнительные пожелания, опции сохранения планировки, кнопка генерации и статусы. Справа/ниже — предпросмотр, результат, сравнение, повторная генерация и скачивание. Разделять демонстрационный и реальный режимы визуально.

### 4.3. Проекты `/projects`
Сетка принадлежащих пользователю проектов. Для каждого: миниатюра, имя, тип комнаты, дата создания/обновления и доступные действия — открыть, переименовать, удалить. Добавить пустое состояние, состояния загрузки и ошибки.

### 4.4. Проект `/projects/[id]`
Исходная фотография, история вариантов и настроек, выделенный результат, повторная генерация и скачивание. Никогда не показывать чужие проекты.

### 4.5. Аккаунт
`/login`, `/signup`, `/settings`: вход/регистрация по электронной почте, подтверждение почты, восстановление пароля, выход, настройка имени и языка, инициирование удаления аккаунта и связанных пользовательских данных.

### 4.6. Сопутствующие страницы
`/pricing` — **информационная** страница будущих тарифов без фиктивной покупки. `/privacy`, `/terms`, `/contact` — структуры страниц и заполняемые тексты, требующие проверки владельцем перед запуском.

## 5. Основной пользовательский сценарий

1. Пользователь открывает `/studio`, выбирает фотографию через диалог файла или drag-and-drop.
2. Система показывает предпросмотр и результаты проверки формата/размера.
3. Пользователь указывает тип помещения, стиль, палитру, масштаб изменений, объекты для изменения, пожелания и параметры сохранения геометрии.
4. При реальном запуске сервер проверяет авторизацию, права, лимиты и допустимость настроек, принимает запрос с ключом идемпотентности и ставит задачу на обработку.
5. Интерфейс показывает честный статус ожидания/обработки без выдуманного процента готовности.
6. Фоновый обработчик использует исходную фотографию в запросе редактирования ИИ, сохраняет результат в приватное хранилище и обновляет статус в базе.
7. Пользователь видит результат, сравнивает до/после, скачивает его или создаёт вариант с другими параметрами.
8. Авторизованный пользователь возвращается к проекту из личного кабинета.

Гостям разрешить попробовать интерфейс в демонстрационном режиме. **Любой реальный платный вызов ИИ должен требовать авторизацию** и соблюдение серверных лимитов.

## 6. Загрузка фотографий

**Поддержка:** JPEG/JPG, PNG, WebP. **Лимит исходного файла:** 10 МБ. Валидация должна проверять содержимое и MIME-тип, а не только расширение. Отклонять SVG, исполняемые и неподдерживаемые файлы. Нормализовать ориентацию, при необходимости ограничивать разрешение, удалять ненужные EXIF-метаданные. Не сжимать пользовательский файл без информирования, если это существенно меняет качество.

Поддержать drag-and-drop, выбор файла, предпросмотр, удаление и повторную загрузку. Для приватных изображений не использовать постоянные публичные URL. В интерфейсе показывать ошибки загрузки и возможность повтора.

## 7. Настройки интерьерной генерации

**Типы помещений:** `living_room`, `bedroom`, `kitchen`, `bathroom`, `dining_room`, `home_office`, `office`, `other`.

**Основные стили:** Modern, Scandinavian, Industrial Loft, Japandi, Classic, Minimalist. Структура справочника должна позволять добавлять Mediterranean, Mid-Century Modern, Boho, Art Deco и другие стили без переписывания формы.

**Палитры:** light, warm_neutral, dark, neutral, custom; в custom — доступные пользовательские цвета.

**Изменяемые элементы:** furniture, walls, floor, ceiling, lighting, decor. Выбор нескольких элементов.

**Степень изменений:** minimal, moderate, full.

**Флаги:** `preserveLayout`, `preserveWindowsAndDoors`, `preserveFurniture`.

**Пожелания:** поле `customPrompt` до 1 000 символов. Валидировать длину и допустимые структуры на сервере. Выбранные настройки сохранять вместе с каждой генерацией.

Важно: запреты на изменение геометрии — это инструкции генеративной модели, а не точная инженерная гарантия. В интерфейсе не обещать неизменность планировки, пригодность изображения для ремонта или соответствие реальным размерам.

## 8. Генерация и сервис ИИ

Реализовать независимый серверный интерфейс `AIImageService`, скрывающий детали конкретного провайдера. Он принимает ссылку на принадлежащее пользователю исходное изображение и валидированные настройки, строит инструкцию, вызывает поддерживаемый API редактирования с **исходным изображением**, проверяет ответ, сохраняет результат и данные операции.

### 8.1. Формирование промпта

Составлять промпт из доверенного шаблона и пользовательских настроек. Описывать стиль, палитру, тип комнаты и нужные изменения. Просить сохранять перспективу, расположение окон и дверей, конструктивные элементы и всё, что пользователь отметил неизменяемым. Предотвращать добавление случайных помещений или архитектурно неправдоподобных изменений. Если пользовательские инструкции конфликтуют с выбранными настройками, возвращать понятное сообщение либо применять документированный приоритет.

Не включать пользовательский `customPrompt` в системные настройки или исполняемые команды. Передавать его только как данные для композиции промпта.

### 8.2. Обработка задач

Статусы: `pending`, `processing`, `completed`, `failed`, `cancelled`. Для длительных генераций использовать очередь и фонового обработчика, совместимых с хостингом; не рассчитывать на бесконечное выполнение HTTP-запроса. Нужны идемпотентность, защита от двойной оплаты/учёта, ограниченные повторные попытки временных ошибок, тайм-ауты и обработка зависших задач. Отображать статус честно; не имитировать реальный процент прогресса.

### 8.3. Сохранение результата

Проверять полученное изображение, записывать его в приватный бакет, фиксировать путь и метаданные. Не сохранять результат с общедоступной постоянной ссылкой. Удалять временные файлы по утверждённой политике хранения.

### 8.4. Режимы

`AI_PROVIDER=mock`: приложение работает без OpenAI API; показывает **явно обозначенные** заранее подготовленные примеры и позволяет проверить весь пользовательский поток. Не притворяться, что mock реально преобразовал загруженное фото.

`AI_PROVIDER=openai`: включить реальную генерацию только при наличии корректной серверной конфигурации. При отсутствии ключа возвращать диагностическое сообщение без разглашения настроек.

Пример `.env.example`:

```dotenv
AI_PROVIDER=mock
OPENAI_API_KEY=
OPENAI_IMAGE_MODEL=
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=
```

Не помещать `SUPABASE_SERVICE_ROLE_KEY` и `OPENAI_API_KEY` в клиентский бандл. Уточнить реальные необходимые переменные при реализации и документировать их.

## 9. Просмотр и история

Реализовать сравнение Before / After с доступным для клавиатуры ползунком, просмотр картинок рядом, увеличение/полный экран, выбор основного результата и скачивание. Если пропорции изображений отличаются, корректно согласовывать сравнение, не растягивая изображения с искажением.

У проекта одно исходное фото и произвольное количество вариантов. Каждая генерация хранит свои настройки, время, статус и результат. При удалении проекта очищать связанные записи и принадлежащие проекту файлы по политике удаления. Критичные операции подтверждать в интерфейсе.

## 10. База данных

Использовать PostgreSQL и миграции. Минимальная логическая схема:

| Таблица | Поля |
|---|---|
| `profiles` | `id`, `email`, `display_name`, `locale`, `created_at` |
| `projects` | `id`, `user_id`, `title`, `room_type`, `original_image_path`, `created_at`, `updated_at` |
| `generations` | `id`, `project_id`, `status`, `style_id`, `settings` (JSONB), `result_image_path`, `error_code`, `created_at`, `completed_at` |
| `styles` | `id`, `slug`, `name`, `prompt_description`, `image_path`, `enabled` |
| `usage_events` | `id`, `user_id`, `generation_id`, `event_type`, `created_at` |
| `plans` | `id`, `name`, `generation_limit`, `enabled` |
| `subscriptions` | `id`, `user_id`, `plan_id`, `status`, `period_end` |

Плановые таблицы `plans` и `subscriptions` разрешено создать без действующего биллинга. Настроить RLS и политику владения для всех приватных данных и файлов. Индексы на `user_id`, `project_id`, поля статуса/времени, где это необходимо. Обеспечить согласованность учёта генераций при повторных запросах.

## 11. Серверное API

| Метод | Путь | Описание |
|---|---|---|
| POST | `/api/projects` | Создать проект |
| GET | `/api/projects` | Получить собственные проекты |
| GET | `/api/projects/[id]` | Получить проект и разрешённые варианты |
| PATCH | `/api/projects/[id]` | Переименовать проект |
| DELETE | `/api/projects/[id]` | Удалить проект |
| POST | `/api/projects/[id]/images` | Загрузить исходное фото |
| POST | `/api/generations` | Создать задачу генерации |
| GET | `/api/generations/[id]` | Получить состояние задачи |
| GET | `/api/generations/[id]/download` | Авторизованное скачивание результата |
| GET | `/api/styles` | Получить доступные стили |
| GET | `/api/health` | Проверить состояние приложения |

Везде валидировать типы и права доступа на сервере; запросы к чужим проектам должны отклоняться. Ошибки возвращать единообразно: HTTP-код, `code`, безопасное человекочитаемое `message` и `requestId`.

**Пример тела POST `/api/generations`:**

```json
{
  "projectId": "PROJECT_UUID",
  "style": "japandi",
  "roomType": "living_room",
  "palette": "warm_neutral",
  "intensity": "moderate",
  "preserveLayout": true,
  "preserveWindowsAndDoors": true,
  "preserveFurniture": false,
  "changeElements": ["furniture", "walls", "lighting"],
  "customPrompt": "Use natural oak and warm lighting.",
  "idempotencyKey": "UNIQUE_REQUEST_ID"
}
```

## 13. Конфиденциальность, безопасность и лимиты

1. Реальная генерация — только для авторизованных пользователей.
2. Серверная проверка RLS и прав владения каждым проектом, генерацией и файлом.
3. Приватное хранилище; короткоживущие ссылки или авторизованная отдача.
4. Проверка MIME, формата, размера и безопасное декодирование загружаемых изображений.
5. Ограничение запросов по пользователю, а при необходимости по IP; одновременная генерация для MVP — одна активная на пользователя.
6. Серверное ограничение расходов на ИИ и учёт фактически предоставленных результатов.
7. Отсутствие секретов, пользовательских изображений и полного промпта в публичных логах.
8. Ограничение текстового ввода и трактовка его как недоверенных данных.
9. Удаление учётной записи и пользовательских данных по принятой политике хранения.
10. Отдельно подготовить и согласовать юридические страницы, сроки хранения фотографий и политику работы с персональными данными до публичного запуска.

Секреты хранить только в переменных окружения и защищённых настройках хостинга. Не коммитить `.env.local` и другие файлы с секретами.

## 14. Производительность и доступность

**Цели:** Lighthouse Performance от 90 на основных публичных страницах на десктопе, Accessibility от 90, LCP до 2,5 секунды на согласованном целевом соединении. Не распространять эти требования на непредсказуемое время генерации ИИ.

Поддержать оптимизированные превью и миниатюры, отложенную загрузку галерей, индикаторы ожидания и корректные пустые состояния. Интерфейс не должен терять настройки при кратковременных сетевых сбоях. Реальное время обработки зависит от провайдера; не обещать фиксированное время и не показывать вымышленный прогресс.

## 15. Основа монетизации

Подготовить модель Free / Basic / Pro / Business. Для Free предусмотрены ограниченные генерации, для платных вариантов — увеличенные лимиты и в дальнейшем дополнительные функции. Конкретные цены и лимиты пока **не фиксировать**. Страница `/pricing` информационная до подключения платежей.

При добавлении биллинга учёт генераций вести на сервере, исключить повторное списание при повторных запросах и восстанавливать лимит, когда результат не предоставлен из-за сбоя. Не создавать работающие элементы покупки до реализации платёжной системы.

## 16. Тестирование

**Unit:** валидация файлов, стилей, параметров, формирование промпта, проверка лимитов и прав доступа.

**Integration:** создание проекта, загрузка фото, постановка задачи, изменение статуса, сохранение результата, история, удаление данных, идемпотентность.

**E2E:** открыть сайт, авторизоваться, загрузить поддерживаемое фото, настроить стиль, выполнить mock-генерацию, увидеть демонстрационный результат, открыть историю проекта и проверить адаптивную версию.

**Отрицательные сценарии:** отсутствие авторизации, неподдерживаемый/крупный файл, недоступность провайдера, превышение лимита, повторный запрос, попытка открыть чужой проект и некорректный ответ ИИ.

Все платные запросы ИИ должны быть заменены mock-адаптером в автоматических тестах. После каждого крупного этапа запускать доступные проверки типов, линтер, тесты и production-сборку; исправлять обнаруженные ошибки.
